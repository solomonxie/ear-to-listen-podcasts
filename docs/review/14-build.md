# 14 Build, config and scripts

Files read in full: `project.yml`, `Makefile`, `.gitignore`, `ExportOptions.plist`, `Config/Signing.xcconfig`, `Config/Local.xcconfig.example` (the only tracked files under `Config/`), `.env.demo.example`, all three `.entitlements`, every file under `scripts/` except the transcribe Python bodies (only skimmed for credentials and env use), `DemoData/README.md`, `DemoData/DemoSecrets.swift`, and the generated `Sources/App/Info.plist` (gitignored, generated by XcodeGen from `project.yml`). Also checked: the build-related parts of `docs/release/README.md`, `listing.md` and `testflight.md`. The locally generated `project.pbxproj` and `Package.resolved` (untracked) were read for effective build settings. Every `#if DEBUG` / `#if SCREENSHOTS` site was checked, along with required-reason API call sites, and git history for secret patterns.

Already covered elsewhere and not repeated: the custom AI endpoint accepting `http://` with no ATS exception (06). CarPlay code shipping in Release without the entitlement (13 P3). `Documents/Downloads` being visible in Files (02).

**Checklist results:**
- Secrets hygiene: clean. All 263 commits were searched with `-S`/`-G` for `AKIA`, `sk-`, `-----BEGIN`, `DEVELOPMENT_TEAM` and 10-character team-ID shapes. The `AKIA` hits are `AKIAEXAMPLE` and `AKIA…` placeholders. The `-----BEGIN` hits are PEM parsing code and a form placeholder. No `sk-` hit is followed by a key-length token. Every `DEVELOPMENT_TEAM` line in history is empty, `YOURTEAMID`, `REPLACE_WITH_YOUR_TEAM_ID` or `${DEVELOPMENT_TEAM}`. Bundle IDs in history are all `com.example.*`. The only author email is the GitHub noreply address. `.env.demo.example` has always held empty values. `Config/Local.xcconfig`, `.env.demo` and `.env*.local` are ignored. `.p8` keys and a bare `.env` aren't (P2 #1).
- DemoData: about 1.3 MB on disk (twelve `.m4a` files at 84–140 KB, plus about 30 KB of JSON). That is roughly 4% of the 35 MB budget, and it ships on purpose for reviewers. `make-audio.py` and `README.md` are excluded. There are no secrets in it. `DemoSecrets.plist` is produced only by `scripts/demo-secrets.sh`. The script deletes the plist first and exits for `CONFIGURATION=Release`, and the reader is compiled only under `#if DEBUG`. Both gates agree, so a stale Debug folder can't leak it into an archive.
- Dependencies: one package (`GRDB`), one product, linked by the app only. The extension and tests don't link it twice. `from: 6.29.3` means "up to the next major", and `Package.resolved` isn't in git (P3 #1).
- Release config (effective, from the generated project): `SWIFT_OPTIMIZATION_LEVEL = -O`, `SWIFT_COMPILATION_MODE = wholemodule`, `ENABLE_TESTABILITY` is `YES` in Debug only, `ENABLE_NS_ASSERTIONS = NO`, `dwarf-with-dsym`. `SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG` is set in Debug only. `SCREENSHOTS` is never set in `project.yml`, the `Makefile` or the scripts. It only comes from a one-off command line documented in `listing.md:193`, and `release-ios.sh` archives in a separate, default DerivedData. So it can't leak into Release. `-Osize` and `DEAD_CODE_STRIPPING` are not set (P3 #2).
- Debug-only code: `AppStorefront` overrides and `DemoSecrets` are behind `#if DEBUG`, and `ScreenshotDriver` plus its four call sites are behind `#if SCREENSHOTS`. `EarStorefront` is written into the Release Info.plist too (empty), but only `#if DEBUG` code reads it.
- Privacy manifest: missing (P1 #1).
- Info.plist: `NSSpeechRecognitionUsageDescription` is present. There's no microphone use (no `AVAudioRecorder`, `inputNode` or `installTap`), so no microphone string is needed. `PhotosPicker` needs no photo-library string. There are no ATS exceptions. S3, Azure, GCS and every built-in AI host use `https`. `ITSAppUsesNonExemptEncryption = false` is correct for HTTPS, Keychain, HMAC and RSA signing used only for authentication. The background mode is `audio` only, and the iCloud container is declared.
- Share extension: the bundle ID is `$(APP_BUNDLE_ID).share`, a correct child of the app's ID. `group.$(APP_BUNDLE_ID)` is the same in all three entitlements files and in both Info.plist `AppGroupIdentifier`s. Both targets take `CURRENT_PROJECT_VERSION` from the command line, so the build numbers match. `MARKETING_VERSION` is set twice (P3 #5).
- Script robustness: all the shell scripts are `#!/bin/sh` with `set -e`, and every expansion that matters is quoted. `pipefail` isn't available in POSIX `sh`, but the only pipelines (UDID discovery, the `.env.demo` loop) are followed by `:?` guards, or end in the command whose status matters. `run_until_done.sh` is bash with `set -uo pipefail`. The build number is a minute-resolution local timestamp (P3 #4).

Summary: the signing setup is in good shape. The team ID and bundle ID are kept out of git by an included, gitignored xcconfig, and history is clean. Debug-only and screenshot-only code is properly gated. The serious gap is that there is no `PrivacyInfo.xcprivacy` at all, while the app and its share extension call `UserDefaults` and read file timestamps, which are both required-reason APIs. App Store Connect flags this as ITMS-91053. Beyond that, `.p8` API keys aren't ignored, even though `altool` looks for them in `./private_keys` under the repo root. The rest is reproducibility, size measurement and release traceability. **P0 0 · P1 1 · P2 1 · P3 10**

## P1

**1. No privacy manifest, but the app and the share extension use required-reason APIs.**
`project.yml:17-31`, `:124-127`; uses at `LocalFilesProvider.swift:114`, `:121`, `:141`, `:155`; `Cache.swift:59`, `:211`, `:215`; `LocalBackups.swift:101`; `PendingRestore.swift:34`; `ShareInbox.swift:12`; `UserDefaults.standard` in about 25 files
- `git ls-files` and `git log --all -- '*xcprivacy*'` show no `PrivacyInfo.xcprivacy`, now or ever. The app reads `contentModificationDateKey`/`creationDateKey` and sets `.modificationDate` (the file-timestamp category). It uses `UserDefaults.standard` (the user-defaults category). The extension uses `UserDefaults(suiteName: appGroup)`. No disk-space or boot-time APIs are used, which is good: nothing to declare there.
- Scenario: the next upload gets ITMS-91053 "Missing API declaration" for `NSPrivacyAccessedAPICategoryUserDefaults` and `NSPrivacyAccessedAPICategoryFileTimestamp`. Apple has required these declarations since May 2024. Depending on enforcement at the time, the build is either rejected at processing or carries the issue into review, on top of the open 4.3 and China resubmission. PLAUSIBLE: earlier uploads may already have produced the warning email. Check the App Store Connect inbox.
- Fix: add `Resources/PrivacyInfo.xcprivacy` (the app) and `Extensions/Share/PrivacyInfo.xcprivacy` (the extension; it's already inside the extension's `sources` path), then run `xcodegen generate`. App: `NSPrivacyTracking false`, empty `NSPrivacyTrackingDomains` and `NSPrivacyCollectedDataTypes` (matches `privacy-policy.md`), and `NSPrivacyAccessedAPITypes`:
  - UserDefaults: `CA92.1` and `1C8F.1`. The app group is read by the extension's inbox code, which is compiled into the app too.
  - FileTimestamp: `C617.1` for files in the container (cache, backups, pending restore) and `3B52.1` for files the user picked in Files (`LocalFilesProvider`).
  - Extension: UserDefaults `1C8F.1`.

## P2

**1. App Store Connect API keys (`.p8`) and a bare `.env` aren't gitignored, and `altool` looks for the key inside the repo.**
`.gitignore:23-27`; `scripts/release-ios.sh:22`, `:73-75`; `Makefile:31`
- `release-ios.sh` `cd`s to the repo root and then runs `xcrun altool --apiKey "$ASC_KEY_ID"`. altool finds `AuthKey_<id>.p8` in `./private_keys` (that is, `<repo>/private_keys`), `~/private_keys`, `~/.private_keys` or `~/.appstoreconnect/private_keys`. `.gitignore` covers `*.pem`, `.env*.local` and `.env.demo`, but not `*.p8`, `private_keys/` or `.env`.
- Scenario: following `make help` ("ASC_KEY_ID + ASC_ISSUER_ID … set … in the same place"), the user drops the key into `private_keys/` next to the script, and the next `git add -A` commits an App Store Connect key. That key can upload builds and manage the app. The same happens with a `.env` created by habit instead of `.env.local`.
- Fix: add `*.p8`, `private_keys/` and `.env` to `.gitignore`. Mention in `make help` that the key belongs in `~/.appstoreconnect/private_keys`.

## P3

**1. `Package.resolved` lives inside the gitignored `.xcodeproj`, so GRDB's exact version isn't recorded.** `project.yml:9-11`; `.gitignore:2`
- `from: 6.29.3` accepts any 6.x. The resolved pin (`6.29.3` at `2cf6c75`) exists only in the local `EarToListen.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`. A fresh clone, a new machine or a wiped project resolves whatever 6.x is latest, so a Release can pick up an unreviewed GRDB change.
- Fix: pin it with `exactVersion: 6.29.3` (bump deliberately), or copy `Package.resolved` to a tracked path and restore it after `xcodegen generate`. Either way, moving to GRDB 7 is a separate, deliberate step.

**2. PLAUSIBLE: Release isn't set up for size. There's no `-Osize`, and `DEAD_CODE_STRIPPING` is unset.** `project.yml:91-113`
- The generated project has `SWIFT_OPTIMIZATION_LEVEL = -O` and no `DEAD_CODE_STRIPPING` at any level. It falls back to Xcode's built-in default, which Xcode's "recommended settings" upgrade turns on explicitly. XcodeGen projects never get that upgrade. Given the 35 MB "falling" budget, both are free size wins to measure.
- Fix: under the app and extension `settings.configs.Release`, set `SWIFT_OPTIMIZATION_LEVEL: -Osize` and `DEAD_CODE_STRIPPING: YES`. Compare with `make size`, and keep `-Osize` only if playback and search stay smooth.

**3. PLAUSIBLE: `make size` measures an unstripped `build`, not what ships.** `Makefile:62-65`; `CLAUDE.md` size snippet
- A `build` action leaves `DEPLOYMENT_POSTPROCESSING = NO`, so the binary keeps its symbol tables. `archive` strips it, and the export adds `stripSwiftSymbols`. The budget number therefore overstates the shipped app, and the gap varies with code size, which blurs "falling, not rising".
- Fix: add `DEPLOYMENT_POSTPROCESSING=YES STRIP_INSTALLED_PRODUCT=YES` to the `size` invocation. Alternatively, have `release-ios.sh` print `du -sh` of `$ARCHIVE/Products/Applications/EarToListen.app`, which is the real number.

**4. The build number is only loosely monotonic, and a build can't be traced back to a commit.** `scripts/release-ios.sh:31-32`; `Makefile:50`
- `date +%Y%m%d%H%M` is local time at minute resolution. Two runs in the same minute (a retry after a failed export) reuse the number and the same `/tmp/eartolisten-release/$BUILD` folder, and the upload is refused as a duplicate. The DST fall-back hour, a timezone change, or a manual `release-ios.sh <n>` can go backwards. The dirty check is `git diff --quiet HEAD --`, which ignores untracked files. XcodeGen still compiles a new, uncommitted `.swift` file into the upload, and nothing records which commit a TestFlight build came from.
- Fix: `date -u +%Y%m%d%H%M%S`, and refuse a manual number that isn't greater than the last one. Write `git rev-parse --short HEAD` (plus `-dirty`) into the Info.plist (for example `EarGitCommit: $(EAR_GIT_COMMIT)`) and into the archive folder name. Make the dirty check `git status --porcelain` and fail unless `ALLOW_DIRTY=1` is set.

**5. `MARKETING_VERSION` is set separately on the app and the extension.** `project.yml:96`, `:152`; `docs/release/README.md:19`
- The release README says to bump "`MARKETING_VERSION` in `project.yml`", singular. Bumping only the app's leaves the extension at `1.0`, and the upload gets ITMS-90473 (extension `CFBundleShortVersionString` mismatch).
- Fix: move `MARKETING_VERSION` (and the `CURRENT_PROJECT_VERSION` default) to `Config/Signing.xcconfig`, or a `settingGroups` entry both targets use.

**6. `DEVELOPMENT_TEAM` is parsed out of `Local.xcconfig` with a bare `sed`.** `scripts/release-ios.sh:26`; `scripts/install-ios-device.sh:9`
- `s/^DEVELOPMENT_TEAM *= *//p` keeps trailing spaces, a trailing `// comment` or a CR. That string is then passed on the command line, where it overrides the correctly parsed xcconfig value, and is substituted into `ExportOptions.plist`. Signing then fails with "no team found". A second matching line yields two lines.
- Fix: `sed -n 's/^DEVELOPMENT_TEAM *= *\([A-Z0-9]*\).*/\1/p' … | head -1`. Or don't pass it at all when it came from the xcconfig, since the build already includes that file.

**7. `demo-secrets.sh` breaks on common `.env` shapes.** `scripts/demo-secrets.sh:13-16`
- A repeated key makes `plutil -insert` fail, which fails the whole Debug build with a plutil error. A CRLF file or a trailing ` # comment` keeps `\r` or the comment in the value, so the demo bucket's secret key is silently wrong and demo sync fails with a signature error.
- Fix: strip `\r` and trailing comments (`sed -e 's/\r$//' -e 's/[[:space:]]#.*$//'`), and use `plutil -replace` (insert or overwrite).

**8. Release archives and dSYMs go to `/tmp`, which macOS clears.** `scripts/release-ios.sh:32`
- `/tmp/eartolisten-release/<build>` is gone after a reboot or a few days of cleanup. The `.xcarchive` doesn't appear in Xcode's Organizer either. `uploadSymbols` covers Apple-side crash symbolication, but there is no local archive to re-export from, and no dSYM for a crash log someone mails in.
- Fix: archive to `~/Library/Developer/Xcode/Archives/$(date +%F)/EarToListen-$BUILD.xcarchive` (Organizer picks it up), or to a gitignored `build/release/`.

**9. The CarPlay entitlements file is a full copy of the base one.** `Sources/App/EarToListen-CarPlay.entitlements`; `Sources/App/EarToListen.entitlements`; `project.yml:109-110`
- They differ by one key. A future entitlement added only to the base file (for example `com.apple.developer.icloud-container-environment`, or a second app group) silently disappears from `CARPLAY=1` builds, where iCloud backup or the share inbox then breaks in testing only.
- Fix: add a comment in both files pointing to the other, or generate the CarPlay variant in `install-ios-device.sh` with `PlistBuddy -c 'Add :com.apple.developer.carplay-audio bool true'` on a copy of the base file.

**10. `run_until_done.sh` retries forever on a permanent failure, and the transcribe tooling is unpinned.** `scripts/transcribe/run_until_done.sh:20-29`; `scripts/transcribe/requirements.txt`
- A wrong path, a missing model or an import error exits non-zero every pass. The loop retries every 60 s indefinitely under `caffeinate`, keeping the Mac awake and appending to the log until someone notices. `torch`, `torchaudio`, `numpy`, `mlx-whisper` and the others have no version bounds, so a new `venv` can resolve to a different, incompatible stack.
- Fix: cap consecutive non-75 failures (for example 5) and then exit with the last code. Run `pip freeze` once into `requirements.lock`.
