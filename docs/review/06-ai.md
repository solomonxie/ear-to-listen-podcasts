# 06 AI (`Library/AI` and the chat client)

Files read in full: `AiClient.swift`, `AiPricing.swift`, `AiRouter.swift`, `AppStorefront.swift`, `OpenAIChatClient.swift`, `OpenAICompatibleChatClient.swift`, `AnthropicChatClient.swift`, `GoogleChatClient.swift`, `EpisodeSummarizer.swift`, `EpisodeMetadataSuggester.swift`, `AlbumMetadataSuggester.swift`, `AlbumProfileSuggester.swift`, `SpeakerProfileSuggester.swift`, `ArtworkSuggester.swift`, `BookmarkInsights.swift`, `DB/Models/AiKey.swift`, `Library/EpisodeSummary.swift`. Also read, to confirm findings: `DB/AiKeyStore.swift`, `DB/AiQueryStore.swift`, `Library/ContentAnalyzer.swift` and its call in `Sync.swift`, `AddAiKeyView`, `AiKeysSettingsView`, `AiKeyDetailView`, `SettingsViewModel.addAiKey`, `EpisodeSummaryView`, `EpisodeDetailsPane.suggest`, `EpisodeEditView`, `AlbumAnalysisView`, `BookmarkInsightsView`, `ArtworkSourceRow`, `TranscriptionEngine` (China strings), `project.yml` (Swift 6.0, no default-MainActor isolation).

Summary: the China gating holds at every call site. `AiKeyStore.all()` filters by storefront, so the router, the image path and Whisper never see a hidden vendor's key. `AiRouter.runChatCompletion(vendor:)` refuses one again, and the add-key picker, the transcription engine list and the Draw button all ask `isOffered`. No vendor name unlicensed in China reaches a China screen through these paths. Keys stay in the Keychain and never reach history rows, logs or error text. The weak point is the storefront answer: it falls back to device region until StoreKit replies (#10). The real problems are size and lifetime. Three passes cap the reply at 300 tokens and then ask for paragraphs or a whole album, so they come back cut off and are thrown away as "unreadable". Prompt budgets are in characters with no idea of the model's context, so Kimi's default 8k model can't take a normal episode. The album review writes suggestions back by an index it recomputes at apply time. Cancelling a call is treated as every key failing. **P0 0 · P1 4 · P2 7 · P3 18**

## P1

**1. Three passes ask for paragraphs or a whole album inside the router's 300-token default. The reply is cut off mid-JSON and thrown away.**
`AiRouter.swift:24`; `AlbumMetadataSuggester.swift:117-119`; `AlbumProfileSuggester.swift:109-111`; `SpeakerProfileSuggester.swift:116-118`
- Only `EpisodeSummarizer` (1,600) and `BookmarkInsights` (1,400) pass their own `maxTokens`. Album metadata wants a title, two sentences of notes and a year *per episode*, plus album fields. Album profile wants "2-4 short paragraphs" plus notes and topics. Speaker profile wants 2-4 paragraphs plus four more fields. All three use 300.
- A cut-off reply still has a `}` in it (the end of some inner object). So `jsonObject(in:)` returns an invalid slice, the decode fails, and the user sees "The AI response wasn't in a form the app could read. Try again." The tokens are still billed. Trying again gets the same result.
- `AiRouter`'s own comment (`:19-23`) describes exactly this failure for the summary. `SpeakerProfileSuggester`'s comment (`:57-60`) puts an unparseable answer down to the input size. It is more likely this cap.
- Scenario: Analyze Album on a 12-episode album. About 12 × 60 tokens of output is needed, and 300 are allowed. Every run fails. A speaker profile in Chinese runs out of tokens part-way through `profile`.
- Fix: give each pass its own `maxTokens` sized to what it asks for (album metadata: about 80 per episode plus 200; profiles: about 1,200). Read `finish_reason` / `stop_reason` / `finishReason` in the clients and raise a distinct "reply was cut off" error instead of the parse error.

**2. Album review writes each suggestion to `ready[index]`, but `ready` is recomputed at Apply time. If a transcript finishes in between, titles land on the wrong episodes.**
`AlbumAnalysisView.swift:24`, `:155-171`; `AlbumMetadataSuggester.swift:83-94`
- `analyze` numbers episodes by their position in `partition(tracks:).ready` at that moment. `apply()` calls `partition.ready` again, and that reads every transcript from the DB again. The `guard suggestion.index < ready.count` check catches only shrinkage.
- Scenario: the user opens Analyze Album while an episode of the same album is playing and transcribing. They read the suggestions for a minute. The pass finishes, and that episode now counts as ready and sorts into the middle of the list. On Apply, every suggestion after it is written to its neighbour, with `metadataEditedAt` set, so sync won't correct it. A before-suggestions backup exists, but nothing tells the user to use it.
- `ready[i]` is also the `tracks` snapshot from when the sheet opened. `saveEdit` writes that whole stale row back.
- Fix: return the `[Track]` (or their ids) that were sent alongside `Result`, and apply by id. Re-fetch each track before editing it.

**3. Prompt budgets are characters with no idea of the model's context. Kimi's default model (offered in China) can't take an ordinary episode summary.**
`EpisodeSummarizer.swift:37`, `:43`; `EpisodeMetadataSuggester.swift:74`; `AlbumMetadataSuggester.swift:64`; `AiKey.swift:77`, `:98`
- The summary sends up to 28,000 characters and reserves 1,600 reply tokens. `moonshot-v1-8k` has an 8,192-token window shared by input and output. 28k characters of English is about 7k tokens, and in Chinese it is well over 8k. Moonshot answers 400, which reaches the user as "Kimi (Moonshot) request failed (400)." (see #11, the reason is dropped).
- The router then tries the next key with the same oversized prompt, which is fine if that key has a large model and a wasted call if not.
- PLAUSIBLE, same shape: Groq's free tier caps `llama-3.1-8b-instant` at about 6k tokens per minute, so the summary is refused with 413.
- Scenario: a China-storefront user adds a Kimi key with the default model and taps ✨ on a 40-minute episode. It fails every time, and the error gives no hint that the model is too small.
- Fix: give `AiVendor` (or the model presets) a context size, and derive the character budget from it at about 3 characters per token for Latin text and 1 for CJK. Or default Kimi to `moonshot-v1-32k`/`kimi-latest`. Surface "this model's context is too small" for a 400 that says so.

**4. Shipped default and preset models that the vendor rejects. Adding the key fails, or every call does.**
`AiKey.swift:71`, `:89`, `:92`; `OpenAICompatibleChatClient.swift:25`; `SettingsViewModel.swift:62-79`
- `o4-mini` is an OpenAI preset. OpenAI's reasoning models reject `max_tokens` (they take `max_completion_tokens`), so the save-time test returns 400 and the key can't be added with that model. If it were sent, reasoning tokens would use up 300 and `content` would come back empty.
- PLAUSIBLE (depends on the vendor's retirement schedule, which can't be verified statically): `gemini-1.5-flash` is Google's *default* and `gemini-1.5-pro` a preset. Google has retired the 1.5 models, so any Google key left on Default gets a 404 ("Google request failed (404).") on the test and on every call. `grok-2-latest` and `moonshot-v1-*` are also old ids worth checking.
- Scenario: a user picks Google with the default model. Save fails with a status code and nothing about the model.
- Fix: send `max_completion_tokens` for OpenAI (it is accepted by all current OpenAI chat models) and keep `max_tokens` for the compatible vendors. Move the Google default to a current Flash model. Re-check every default and preset against each vendor's model list before each release.

## P2

**5. Cancelling a call is treated as every key failing: N fake "network" errors are logged, request counts go up, and a reply that has already been paid for is thrown away.**
`AiRouter.swift:58-77`; `OpenAICompatibleChatClient.swift:31-35`; `AnthropicChatClient.swift:34-38`; `GoogleChatClient.swift:40-44`; `ArtworkSuggester.swift:119-139`; `EpisodeSummaryView.swift:101-104`; `BookmarkInsightsView.swift:63-66`; `ArtworkSourceRow.swift:80`
- The clients turn any `URLSession` error, `URLError.cancelled` included, into `AiClientError(.network)`. The router catches it, records "Network request to X failed." against the key, and moves on to the next key. That key's request is cancelled at once, and so on through the list. There is no `Task.checkCancellation()` and no `CancellationError` passthrough.
- The summary runs in `.task(id: analyzeRequest)` and insights run in the sheet's `.task`. Both are cancelled when the view goes away. A 1,600-token summary takes 20-40 s, and the vendor bills it even though the reply is dropped.
- Scenario: the user taps ✨, then swipes the player down. The summary is lost, and every key's history shows a fresh network failure, which is the thing that history exists to flag.
- Fix: rethrow `CancellationError` (map `URLError.cancelled`) in the clients and stop the router loop on it without recording anything. Run the summary in an unstructured task owned by something that outlives the view (or `Task.detached` whose result goes to the DB), so the paid reply is stored even if nobody is watching.

**6. Sync asks the AI once per imported file, one after another, and a fenced reply wastes the call.**
`ContentAnalyzer.swift:19-41`; `Sync.swift:316-322`
- Each new file with any missing tag gets its own round-trip in the import loop (`stage(.askingAI)`). A first sync of 1,000 badly-tagged files adds 1,000 serial requests, which is tens of minutes. This is the "per-item I/O in a loop" shape CLAUDE.md forbids.
- The reply is decoded directly (`content.data` → `Guess`), without `jsonObject(in:)`. A ` ```json ` fence, which the other passes expect from models, gives nil every time.
- PLAUSIBLE: `guess?.title ?? metadata.title` prefers the path-based guess over an embedded title whenever *any* of the three tags is missing. A good ID3 title can be replaced by a guess made from the file name.
- Fix: batch, e.g. 50 paths per request with an index per line, after the listing. Or move it to a background pass after sync. Use `jsonObject(in:)` and a lenient decoder. Only fill fields that are actually empty.

**7. Per-track transcript reads and decodes on the main actor, several times per render, in Analyze Album and in the edit sheet.**
`AlbumAnalysisView.swift:24`, `:46`, `:58-59`, `:94`, `:113-115`; `AlbumMetadataSuggester.swift:72-80`, `:127-131`; `EpisodeEditView.swift:215`
- `partition` is a computed property. Each read calls `readiness(track:)` for every track, which is one `TranscriptStore.find` and a full JSON decode each, and the body reads it up to five times. On a 40-episode album that is about 200 transcript decodes on main per render, and the toolbar re-renders on `isAnalyzing`.
- `analyze` then reads every transcript twice more (partition, then `transcript(for:)`).
- `EpisodeEditView` runs `readiness(track:)` synchronously in a main-actor `.task`. `EpisodeDetailsPane` already moved the same call off-main (`:110-116`).
- Fix: compute the partition once, off-main with the batched `TranscriptStore.find(trackIDs:)` (as `AlbumDetailView.read` does), store it in `@State`, and pass its segments into `analyze`. Detach the edit-view readiness call.

**8. Album analysis's "total" budget isn't a total. Large albums send far more than 24k characters and ask for more output than models give.**
`AlbumMetadataSuggester.swift:64-66`, `:86`
- `budgetEach = max(600, 24_000 / n)`, so past 40 ready episodes the prompt grows by 600 characters plus a header (file path, title) per episode. With 150 episodes that is over 100k characters.
- The reply then has to hold 150 titles and notes, more than many models' output limit, before #1's 300 cap even applies.
- Fix: split ready episodes into batches of about 15 per request and merge the results. Keep the album-level fields from the first batch, or ask for them in a final small call.

**9. PLAUSIBLE: chat requests use URLSession's default 60 s timeout. A slow long reply times out and the router sends it again on the next key, and both calls are billed.**
`OpenAICompatibleChatClient.swift:19-32`; `AnthropicChatClient.swift:23-35`; `GoogleChatClient.swift:26-41`; `AiRouter.swift:68-76`
- None of the requests is streamed, so no bytes arrive until the whole reply is ready. The summary asks for 1,600 tokens, and a slower or reasoning-tier model can take longer than 60 s. The image path already sets 120 s (`ArtworkSuggester.swift:157`).
- The timeout surfaces as `.network`, the router falls through to the next key with the same prompt, and the first vendor still finishes and bills.
- Fix: set `timeoutInterval` from `maxTokens` (e.g. 120 s for the long passes). Don't fall through to another key on a timeout, only on auth, 429 and 5xx.

**10. PLAUSIBLE: China gating depends on device region until StoreKit answers, and it is never refreshed after launch.**
`AppStorefront.swift:27-36`; `EarToListenApp.swift:35`; `AppLanguage.swift:72`
- Before the first `refresh()` lands, or for good if `Storefront.current` is nil (no App Store account, offline at first launch), `isChina` is `Locale.current.region == "CN"`. A China-storefront device with its region set to Hong Kong or the US gets every vendor, OpenAI included, in the add-key picker and Whisper in the transcript pane.
- `AppLanguage.initial` reads `isChina` during launch, before `refresh()` has returned on a first run, so a China install with a non-CN region doesn't get the Chinese default.
- `Storefront.updates` isn't observed, so a storefront change mid-session isn't picked up.
- Fix: treat "unknown" as China for vendor gating (fail closed) until a StoreKit answer is cached. Await `refresh()` before first deciding the language. Listen to `Storefront.updates`.

**11. Vendor error bodies are thrown away, and Gemini's 400 is always reported as a bad key.**
`OpenAICompatibleChatClient.swift:37-46`; `AnthropicChatClient.swift:40-45`; `GoogleChatClient.swift:46-56`; `AddAiKeyView.swift:105`
- Every non-200 becomes "X request failed (status)", with the JSON `error.message` (which says *why*: context too long, unknown model, quota) never read. `ArtworkSuggester.errorMessage(in:)` already does this for images.
- Google maps every 400 to "Google rejected the API key." Gemini also returns 400 for an invalid argument, an over-long prompt or a bad model name.
- Scenario: a working Google key with an oversized summary prompt. The user is told the key was rejected and deletes a good key.
- Fix: decode `error.message` (all three shapes) into the message. For Google, map 400 to `invalidKey` only when `error.status` is `INVALID_ARGUMENT` with reason `API_KEY_INVALID`.

## Improvements (P3)

- AI error strings are plain `String` literals, not `String(localized:)`, so a China install (which defaults to Chinese) shows them in English. Three of them point to "Settings ▸ AI Features", which doesn't exist (the screen is AI ▸ AI Keys). `AiRouter.swift:5`; `ArtworkSuggester.swift:88`, `:94`; `EpisodeSummarizer.swift:25`, `:30`; the three clients; `TranscriptionEngine.swift:121`
- Settings copy says keys are used "to transcribe an episode on playback". Whisper isn't offered in China, so that copy describes a feature China users don't have. `AiKeysSettingsView.swift:15`, `:27`; `AiKeyDetailView.swift:70`
- The artwork Search button opens google.com on the China storefront too, where it doesn't load. Gate it with the other China gates, or offer a local engine. `ArtworkSourceRow.swift:56-61`
- The Gemini key goes in the URL query (visible to proxies and in URL-bearing errors). Use the `x-goog-api-key` header. A model id with a space or `/` makes `URL(string:)` nil, which is reported as "That doesn't look like a usable Google API key". `GoogleChatClient.swift:20-24`
- `jsonObject(in:)` takes the first `{` to the last `}`, so prose with braces after the JSON breaks it. Send `response_format: {"type":"json_object"}` to the OpenAI-compatible vendors that support it. `EpisodeMetadataSuggester.swift:161-166`
- `Message.content` is non-optional, so a `null` content (OpenAI refusal, or a reasoning model that ran out of tokens) reads as "Unexpected response shape". `OpenAICompatibleChatClient.swift:50`
- Anthropic: 403 isn't mapped to `invalidKey`, and only the first content block's text is read. `AnthropicChatClient.swift:42`, `:59`
- The router cursor is a UserDefaults read-modify-write. Concurrent calls (a sync guess and a summary) can both start from the same key under round-robin. `AiRouter.swift:47-52`, `:73-75`
- A Keychain read failure (`try? store.secret`) skips the key silently. If it is the only key, the user is told "No AI key configured". `AiRouter.swift:59`, `:78`
- `AiKeyStore.all()` runs the legacy-migration check on every call. With no keys, that is a DB count plus a Keychain read per synced file through `ContentAnalyzer`. Run it once at launch. `AiKeyStore.swift:13`, `:80-86`
- `EpisodeDetailsPane.suggest` bumps `analyzeRequest` even when the metadata call failed, so a bad key or no key fails twice per tap. `EpisodeDetailsPane.swift:416-437`
- The summary is only reachable when the transcript is complete (`onSuggest` is gated on `readiness.isReady`). `EpisodeSummarizer` explicitly supports a partial one. `EpisodeDetailsPane.swift:76`; `EpisodeSummarizer.swift:47-49`
- The insights sheet spends a call on open whenever nothing is saved, including after a failed run. Make generation an explicit tap. `BookmarkInsightsView.swift:63-66`
- `BookmarkInsights.block` always includes the first episode whatever its size, so one heavily-marked episode can blow the budget. Trim its marks instead. `BookmarkInsights.swift:136-141`
- `EpisodeMetadataSuggester.suggest` fetches and decodes the transcript twice (readiness, then excerpt). `EpisodeMetadataSuggester.swift:101-103`, `:134-136`
- `AiPricing` has no entry for Qwen, Kimi, GLM or Doubao, which are four of the five named vendors offered in China, so their cost always shows "—". `AiPricing.swift:10-23`
- PLAUSIBLE: a custom endpoint accepts `http://`, but there is no ATS exception, so a plain-HTTP host name (a LAN Ollama by name) fails as "Network request to host failed". Either add `NSAllowsLocalNetworking` or reject `http` with a clear message. `OpenAICompatibleChatClient.swift:106`
- `fetchImage` checks the 12 MB cap only after the whole body has been downloaded. `ArtworkSuggester.swift:200-202`
